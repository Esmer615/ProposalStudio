# 模型选型与 Agent 工作流方案（调研版）

> 结论先行：**这是运筹学问题，但 GitHub 上没有可直接用的成品**。
> 必须自建优化器，用 OR-Tools 做内核；Agent 只负责"翻译需求 + 解释结果"，不碰算术。
> 本文包含 4 层 × 每层 3–5 个可选方案，以及我已跑通的真实数据原型。

## 一、把问题说清楚：它其实是 3 个模型叠在一起

你直觉对了。这个赛题表面是"做 HTML 提案"，内核是三层运筹：

| 层 | 数学本质 | 学术名 | 难度 |
|---|---|---|---|
| L1 选哪些线路/点位 | 预算 = 容量、每条线有库存上限、有最低投放量 | **有界背包 / 多重背包 (Bounded Knapsack)** | 低 |
| L2 覆盖面能否达标 | 门店/地标半径覆盖到的人群要被选中的媒体"打中" | **最大覆盖选址 (MCLP, Church 1974)** | 中 |
| L3 档期与施工能否落地 | 单晚上限、雨天顺延、误一补二缓冲、库存被占要换线 | **资源受限排程 (RCPSP) + 约束满足 (CSP)** | 中高 |

三层是**耦合**的：L1 选出的线路决定了 L2 的覆盖、决定了 L3 的施工量。
所以正确做法是**一个模型同时解三层**（MILP），而不是串联三个独立模型 —— 串联会互相打架（选中的线施工排不下、覆盖不够）。

这就是为什么"Agent 自己算"行不通：Agent 无法保证三层约束同时满足，也无法保证换预算后结果可复现。

## 三、四层架构：每层的可选方案

```
┌─ L0 需求输入 ────────────────────────────────────┐
│ 行业 + 预算 + 媒体类型 + 档期                      │
└──────────────────┬───────────────────────────────┘
                   ↓
┌─ L1 策略层（Agent + PM Skill）────────────────────┐
│ PM 写的行业 skill → 权重 JSON（人群/区域/等级/合规） │
└──────────────────┬───────────────────────────────┘
                   ↓
┌─ L2 数据层（⚠️ 断点，见第五节）────────────────────┐
│ 红豆库存快照 + 可视化平台覆盖 + 刊例价              │
└──────────────────┬───────────────────────────────┘
                   ↓
┌─ L3 求解层（专用模型，绝不让 Agent 算）─────────────┐
│ MILP / CP-SAT：选点 + 覆盖 + 排期 一次解完          │
└──────────────────┬───────────────────────────────┘
                   ↓
┌─ L4 输出层（Agent 生成话术 + 确定性渲染 HTML）──────┐
└──────────────────────────────────────────────────┘
```

### L3 求解层：4 个可选方案

| 方案 | 实现 | 求解速度 | 优点 | 缺点 | 适配度 |
|---|---|---|---|---|---|
| **A. OR-Tools CP-SAT** | `cp_model` + 布尔/整数变量 | 10–500ms | 能同时处理"选/不选"逻辑约束与整数数量；支持"次优解池"方便讲取舍 | 目标函数必须是线性的 | ⭐⭐⭐⭐⭐ |
| **B. HiGHS via `scipy.optimize.milp`** | 数组建模 | 5–50ms | 零额外依赖（scipy 自带）；最快 | 无内置约束 DSL，写起来啰嗦；不支持"次优解" | ⭐⭐⭐⭐ |
| **C. 两阶段：贪心 + 局部搜索** | 自写 | <10ms | 极快、易解释、可复现 | 不保证最优；多人写容易不可复现 | ⭐⭐⭐ |
| **D. 多目标进化 (pymoo NSGA-II)** | `pymoo` | 秒–分钟 | 能画"预算 vs 覆盖"帕累托前沿，演示极好看 | 慢、随机性使结果不可复现（违反现场改预算要求） | ⭐⭐ |

> **建议：A 为主，B 做降级备份。**
> 理由：现场评委改预算要求"立刻出结果 + 可复现"。CP-SAT 确定性 + <500ms（我已实测）。
> C 可以作为"解释器"——用来回答"为什么没选 X 线"（把最优解固定，逐条反事实求解）。

### L3 具体模型（我已按真实台账写好）

**决策变量**
- `x[i]` ∈ [0, free(i)] 整数 = 线路 i 投放的车数
- `b[i]` ∈ {0,1} = 是否选用线路 i

**约束**
```
1. 预算:        Σ price(i) × x[i] × 月数 ≤ 预算
2. 库存:        x[i] ≤ free(i) × b[i]        （红豆空车数）
3. 最低量:      x[i] ≥ b[i]                   （选中至少 1 辆）
4. 线路数:      Σ b[i] ≤ K                    （K 由施工产能反推）
5. 施工产能:    Σ x[i] ≤ 可用夜数 × 单晚上限   （02-流程卡点）
6. 等级配比:    高等级车数 / 总车数 ∈ [lo, hi]  （PM skill 给）
7. 区域覆盖:    每个目标区域 Σ b[i] ≥ 1        （MCLP 简化版）
8. 单公司上限:  Σ_{i∈公司c} x[i] ≤ cap_c      （分散执行风险）
9. 档期可售:    x[i] ≤ available(i, 档期)      （按日期查红豆）
```

**目标**（可切换，评委问什么换什么）
```
max  Σ w(i) × x[i]                     w = 等级权重 × 覆盖人口代理
max  Σ w(i) × x[i] − λ × 集中度惩罚     （越分散越好）
min  Σ price(i) × x[i]                  （固定覆盖达标下的省钱）
```

### L3 效果估算层：4 个方案（这是你最关心的"不能由 Agent 算"）

| 方案 | 算法 | 需要什么数据 | 可信度 | 实现成本 |
|---|---|---|---|---|
| **① 线性加权曝光** | `曝光 = Σ 单车日均客流 × 车数 × 天 × 可视系数` | 线路日均客流（可视化平台可得） | 低（会高估，忽略重复触达） | 半天 |
| **② 解析式 Reach/Frequency** | OOH 行业标准：**负二项 / Beta-Binomial 到达模型**，`GRP → Reach` 用 `R = 1−(1+GRP/a)^(−a)` 映射 | 同上 + 一组行业参数 a | **中高**（行业公认做法） | 1 天 |
| **③ 拟合 MMM** | pymc-marketing 的 adstock+saturation | **历史投放数据**（赛题没有） | 高（若数据够） | 做不完 |
| **④ LLM 直接估** | Agent 自己"感觉" | 无 | ❌ 不可复现、不可辩护 | 0 |
| **⑤ 规则查表** | PM skill 里写死"每万元≈X 人次" | PM 经验 | 中 | 2 小时 |

> **建议：② 为主，① 做交叉校验，⑤ 做兜底。明确拒绝 ④。**
> ② 的好处是**公式可写进 HTML 页面**，评委问"你怎么算的"能当场摊开。

**注意：我实测发现 Beta-Binomial 形式在这个数据上会给 100% 到达率**（GRP 213 时就饱和了），这是明显不可信的数字 —— 会被评委当场质疑。所以原型里改成了带物理上限的饱和曲线：

```
单车月曝光 = 日均客流(按等级) × 30天 × 可视率(0.60)
GRP        = Σ(单车月曝光 × 车数) / 目标人群基数 × 100
到达率 R   = reach_cap × (1 − exp(−GRP / k))
              reach_cap = 0.85   物理媒体到不了 100%
              k         = 250    k 越大越保守，放 PM skill 里按行业调
频次 F     = (GRP/100) / R
CPM        = 总花费(元) / 总曝光 × 1000
```

**实测结果（银行保险 skill，目标人群 300 万）**

| 预算 | 车辆 | GRP | 到达率 | 频次 | CPM | 求解 |
|---|---|---|---|---|---|---|
| 100万 | 20 | 565 | 70.5% | 8.0 | 59.0元 | 39ms |
| 200万 | 41 | 1140 | 82.6% | 13.8 | 58.5元 | 44ms |
| 500万 | 104 | 2864 | 85.0%（封顶） | 33.7 | 58.2元 | 52ms |

这三个数字讲得通：**预算翻 5 倍，到达率只从 70% 涨到 85%（封顶），但频次从 8 涨到 34** —— 这正是户外媒体的边际递减特征，可以直接作为答辩时的核心论点（"500 万不该继续堆车身，应该换媒体形式"）。

参数 `k` 也可以放进 PM skill：饮料 k 取小（易到达）、医院 k 取大（需反复触达）。

## 四、Agent 工作流设计（PM Skill 可插拔）

```
【编排层】Orchestrator（一个轻量 Python 服务，不用 Agent）
   │
   ├── 1. 载入 PM Skill（Markdown/YAML）
   │       ├── skills/ban_insurance.md      → 权重、合规红线、话术
   │       ├── skills/beverage.md
   │       ├── skills/health_supplement.md
   │       ├── skills/private_hospital.md
   │       └── skills/theme_park.md
   │       ↓ 输出严格 JSON（schema 校验，不合法就重试）
   │
   ├── 2. 数据加载（见第五节）
   │
   ├── 3. 调用求解器（确定性，纯函数）
   │       solve(inputs, weights) → plan
   │       失败即降级：CP-SAT → HiGHS → 贪心
   │
   ├── 4. 校验器（独立于求解器，防串通）
   │       ├── 预算是否超
   │       ├── 库存是否超
   │       ├── 档期是否可售
   │       ├── 施工是否排得下
   │       └── 合规词是否出现（"保本""治愈""疗效"）
   │
   └── 5. 渲染（模板 + 数据，不让 LLM 写数字）
           Jinja2 → 单文件 HTML（离线可用）
```

**关键设计原则（每一条都能在答辩时说）**

1. **Agent 只输出结构化 JSON，不输出数字** —— 数字全部来自求解器
2. **Skill 是数据不是代码** —— PM 写 Markdown，不用会编程
3. **Skill schema 校验** —— 缺字段就报错，不会静默出错
4. **求解器纯函数 + 固定种子** —— 同输入必同输出（现场可复现）
5. **校验器与求解器分离** —— 求解器出错能被抓住

**PM Skill 模板（这就是 PM 要写的东西）**

```markdown
---
industry: 银行保险
compliance_forbidden: ["保本", "收益承诺", "稳赚"]
default_budget: 100
---
## 人群
primary: 25-45 岁城市白领，地铁通勤为主
## 区域优先级（权重）
陆家嘴: 1.0
静安寺: 0.9
徐家汇: 0.7
网点周边 1km: 0.85
## 媒体偏好
地铁出入口: 0.7    # 信任感
公交车身: 0.3
## 线路等级权重
S: 1.3  A++: 1.0  A+: 0.8
## 效果参数
reach_a: 2.2       # 高频次容忍，a 偏小
## 话术要点
- 强调"网点可达"而非"品牌曝光"
- 合规表述优先
```

## 六、我用真实数据跑通的原型（可复现）

已保存到 `prototypes/`，用 431 条真实台账 + 真实刊例中值。

### 原型 1：基础 MILP

```
输入: 100万 / 1个月 / 10个施工夜 / 单晚25辆
结果: lines=3  cars=17  cost=100.00万  solve=49ms
```
**发现一个业务问题**：解出 537 路一辆车投 13 辆（78万），极度集中。
→ 说明**必须加单线上限**，否则模型会给一个销售无法落地的方案。

### 原型 2：加覆盖/分散约束 + 预算缩放

```
budget | lines | cars | cost  | solve
  100万 |  13   |  18  | 100.0 | 310ms
  200万 |  12   |  36  | 200.0 |  13ms
  500万 |  26   |  91  | 500.0 |  42ms
```
**三个可用的业务结论：**

1. **复用性天然成立** —— 同一个模型，预算只是参数，100/200/500 全部 <400ms 解出。这正是赛题最看重的点。
2. **等级配比约束有效** —— 100万时高等级刚好卡在 ~72%（S 13辆 + A+ 4辆 + AA 1辆），说明约束在起作用。
3. **100万只够 18 辆车** —— 这是个「反直觉的业务事实」：公交车身按刊例价买，100万只够一条主力线加零星几条。这个洞察本身就能当答辩亮点（"为什么建议客户 100 万走地铁、200 万以上才走公交"）。

## 七、方案组合推荐（按投入产出排序）

### 方案 甲：稳赢型（推荐）

| 层 | 选型 |
|---|---|
| 策略 | PM Skill（Markdown）+ 一轮 LLM 结构化输出 |
| 数据 | 一次性导出 → 本地 SQLite 快照 |
| 求解 | **OR-Tools CP-SAT** 单一 MILP |
| 效果 | 解析式 Beta-Binomial Reach/Frequency |
| 输出 | Jinja2 模板渲染单文件 HTML |
| 演示 | 预算滑杆 → 重解 → 表格/图刷新 |

**为什么推荐**：链路最短、确定性最强、当场改预算必出结果。20 分 AI 分会靠"skill 可插拔 + 求解器过程可视化"拿，不是靠让 Agent 做算术。

### 方案 乙：AI 感更强的变体

在甲的基础上加 **Agent 过程回放面板**：把"PM skill 读取 → 权重生成 → 约束生成 → 求解轨迹 → 校验"做成可视化时间线，让评委看到 AI 在每一步做了什么。**求解器仍然是黑盒调用的**。

### 方案 丙：多目标帕累托前沿（炫技型）

用 `pymoo` NSGA-II 跑 50 组预算-覆盖方案，画帕累托曲线。
**代价**：随机性 → 现场重跑结果会变，需要锁种子。**只在时间充足时做**，作为附加页。

### 方案 丁：保守型

完全不用 MILP，用"贪心 + 边际收益排序"。
**优点**：10 行代码、极快、解释性强。

# 红豆库存数据质量与引用口径

> 实测时间：2026-11-21；环境：`https://flairmedia.com.cn:881`，tenant-id=1，比赛测试账号。
> 数字会随真实销售占用变化；下表的数字是 sanity check 基准，不是常量。

---

## 1. 两层口径，不要混用

| 层 | 来源 | 行数特征 | 用途 |
|---|---|---|---|
| **原始 API 快照** | `fetch.py` / `snapshot.py` 抓的 40 列 CSV | 公交 431 行、地铁 861 行（2026-11-21） | 库存事实来源 |
| **管线处理后** | `scripts/build_dataset.py` 过滤/去重/映射后的 `inventory.json` / `candidates.json` | 2027-01：公交 345 行、地铁 735 行 | 引擎求解与页面展示 |

管线会额外做三件事，所以数字会比原始快照小：

1. 丢掉 `freeCount <= 0` 的行；
2. 丢掉 `specialSituation` 命中封闭/改造/施工/停用/停运的地铁点位；
3. 跨月按业务键取 `min_free`（不是相加），任一月为 0 或被封闭则整体不可用。

**引用库存时先说明是哪一层口径。**

## 2. 实测基准（2026-11-21）

### 2027-01 原始 API 快照

| 媒体 | 行数 | totalCount | contractCount | reservationCount | **freeCount 合计** |
|---|---|---|---|---|---|
| 公交 | 431 | 2,525 | 758 | 404 | **1,237** |
| 地铁 | 861 | 861 | 96 | 22 | **743** |

> 地铁 `freeCount` 基本是 0/1 点位状态，合计 743 ≈ “有空位的点位 743 个”。
> 公交 `freeCount` 是空车辆数，合计 1,237 辆。

|---|---|---|
| 2027-01 | 345 / 1,237 | 735 / 735 |
| 2027-06 | 369 / 1,606 | 833 / 833 |
| 2027-07 | 334 / 1,470 | 836 / 836 |
| 2027-08 | 329 / 1,545 | 836 / 836 |

## 3. 静态台账不能当库存

资料包里的静态台账写的是公交 **空位 2,517 / 总 2,525**（几乎全可售）。
按真实档期查询 2027-01 只有 **1,237** 可售，差了一倍。

**结论：**

- 静态台账是某个历史时点的快照，不是“当前库存”；
- 任何方案/答辩数字都必须来自按目标档期的 API 查询；
- 页面上要标注“库存校验时间戳 + 校验档期”。

## 4. 日期参数真实生效

同一个接口，只改 `startDate`/`endDate`，库存完全不同：

### 公交 431 条的可售空位总量（原始快照）

| 档期 | 可售空位 |
|---|---|
| 2026-11-21（今天） | 888 |
| 2027-01 | 1,237 |
| 2027-07 | 1,470 |
| 2027-12 | 2,128 |

### 地铁 861 个点位的可售空位合计

| 档期 | 可售空位 | 合同占用 |
|---|---|---|
| 2026-11-21 | 334 | 527 |
| 2027-01 | 743 | 96 |
| 2027-07 | 845 | 14 |

> 档期越远，库存越空（还没被卖出去）。这正是“按档期查库存”的价值。
> 单条线路（100 路）跨档期也会变：2027-01 空 2；2026-11-21 空 1。

## 5. 引用模板（回答/方案里直接套）

### 公交

> 红豆库存 API（公交，档期 `2027-07-01 ~ 2027-07-31`，查询于 `2026-11-21T...Z`）：
> 431 条线路级库存，可售空位 **1,470** 辆；上刊前需按执行档期重核占用。

### 地铁

> 红豆库存 API（地铁，档期 `2027-01-01 ~ 2027-01-31`，查询于 `2026-11-21T...Z`）：
> 861 个出入口点位，`freeCount` 合计 **743**，有空位点位 **743** 个；
> 其中 9 个点位处于封闭/改造状态（2026-11-21 实测），方案已剔除。

### 单线路/站点

> 100 路（档期 `2027-01-01 ~ 2027-01-31`）：总 8 车，合同 1，预定 5，可售 2。
> 来源：红豆库存 API，查询于 `...Z`。

### 必须避免的说法

| 不要说 | 应该说 |
|---|---|
| “我们有 2,517 辆空车” | “按 2027-07 档期查询可售 1,470 辆” |
| “红豆系统总库存 552/861” | “公交实际返回 431 条线路级记录；接口 total 不可信” |
| “地铁等级 S/A++” | “地铁 lineLevel 2/3，映射 A++/A+（口径待确认）” |
| “覆盖 743 个地铁站” | “861 个**出入口点位**，其中 743 个有空位” |
| “库存是昨天的” | “查询时间戳 `...Z`，档期 `...`” |

## 6. 与项目管线的衔接

```
snapshot.py --from-month 2027-01 --to-month 2027-10
   └─ data/snapshots/bus_2027-01-01_2027-01-31.csv
      data/snapshots/metro_2027-01-01_2027-01-31.csv
         ↓
scripts/build_dataset.py      # 过滤/去重/等级映射/跨月 min_free
         ↓
scripts/validate_dataset.py   # manifest 对账
         ↓
engine/data_loader.py         # 求解时按请求档期读 CSV
```

### 必须遵守的文件命名

`{media}_{YYYY-MM-01}_{YYYY-MM-lastday}.csv`，例如：

```
bus_2027-07-01_2027-07-31.csv
metro_2027-07-01_2027-07-31.csv
```

`engine/data_loader.py` 和 `build_dataset.py` 从文件名解析月份；命名不对就找不到快照。

### 不要用 ad-hoc fetch 覆盖管线快照

- `fetch.py` 默认写 `data/hongdou/`，有筛选时文件名带 `_filtered`；
- `snapshot.py` 默认写 `data/snapshots/`，只写全量原始快照；
- 如果你手工把筛选后的 CSV 放进 `data/snapshots/`，引擎会以为那个月只有这些库存，
  导致 `DATA_UNAVAILABLE` 或方案被错误收紧。

### 快照不要预过滤

`snapshot.py` 写原始 40 列。`freeCount=0`、封闭改造点位都由 `build_dataset.py` /
`engine/data_loader.py` 统一过滤；在抓取阶段删行会破坏跨月 `min_free` 和审计对账。

## 7. 自检清单

回答库存问题前逐条过：

- [ ] 档期明确（`startDate ~ endDate`），不是“当前”或“台账”；
- [ ] 查询时间戳明确（`inventory_ts`）；
- [ ] 媒体明确（公交/地铁），没有把两者相加；
- [ ] 用的是 `freeCount` 合计还是 `freeCount>0` 点位数，说清楚；
- [ ] 地铁封闭/改造点位是否剔除，说明数量；
- [ ] 未知等级（`lineLevel=6` 或空）是否单独提示；
- [ ] 没有把接口 `total` 当库存量；
- [ ] 没有把 `businessAreaName/categoryTags="0"` 当成有效商圈/标签；
- [ ] 没有把线路几何/客流说成来自红豆库存 API（那是大数据平台的）。
